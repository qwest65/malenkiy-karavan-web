# Контекст проекта: как мы работаем и что узнали на «Маленьком караване»

Этот файл переносит в ветку `new-site` всё полезное из истории «Маленького каравана»: договорённости, устройство
выкладки, грабли. Его читает и человек, и ассистент перед тем, как менять сайт. Оригинал «Маленького каравана» остаётся
в ветке `main` (посмотреть любой файл оттуда: `git show main:путь/к/файлу`).

## 1. Договорённости с заказчиком

- **Язык**: всё общение, README, комментарии и тексты сайта по-русски. Отвечать коротко, по делу, без воды.
- **Публикация только с разрешения.** Порядок: правка в рабочей ветке → pull request → проверка CI → показываем результат →
  слияние **только после прямого «сливай»** (слияние делается с проверкой номера коммита). Неясное «ну ладно» разрешением не считается:
  переспросить. После слияния рабочую ветку выравниваем по ветке, в которую слили.
- **README обновляется сразу**, в том же PR, что и изменение. «Что ещё не сделано» и история версий не отстают.
- **Честность.** Не выдумываем данные (отзывы, цифры, адреса, ссылки). Если не проверяли вживую (сайт, панель, телефон), так и пишем.
  Заглушки в данных помечены, и проверка не даст запустить сайт с заглушками (`"draft": false`).
- **Секреты.** Токены, пароли, ключи в чат не присылают и ассистенту не нужны: вводятся только в настройках GitHub (Secrets)
  или в панели сервиса. Скриншоты с паролями не присылать. Личные данные заказчика в посторонние сервисы не отправляем.
- **Без обходных путей**: не отключаем и не пропускаем тесты, не делаем пустые коммиты ради запуска CI, не пишем
  в чужие ветки. Файлы, которые ассистент не читал, он не публикует.
- **Ветка и PR.** Для этого сайта: рабочая ветка → PR **в `new-site`**. В `main` (там «Маленький караван») ничего отсюда не сливаем.

## 2. Как устроена выкладка (опыт основного сайта)

- Сайт статичный, лежит в репозитории готовым HTML. **Свой сервер** сам делает `git pull` нужной ветки раз в 2 минуты;
  папка сайта вида `/srv/sites/<домен в punycode>/`. Удалённые в репозитории файлы с сервера пропадают сами (это обычный checkout).
- Домен: регистрация у регистратора (в нашем случае REG.RU), DNS у отдельного DNS-хостинга (FreeDNS). Кириллические
  домены в служебных местах пишутся в punycode (`xn--…`).
- Сертификат HTTPS (Let's Encrypt) и перенаправления со старых доменов (`301`, https) делает Nginx Proxy Manager на сервере.
  Для продления сертификата сервер должен быть включён и доступен из интернета по портам 80 и 443.
- Для нового сайта: отдельный клон ветки `new-site` в отдельной папке (`git clone -b new-site …`), отдельный домен или
  поддомен, отдельный сертификат. Данные и ключи основного сайта не трогать.
- Чтобы убедиться, что выкладка дошла, нельзя полагаться на зелёный значок CI: открыть сайт и сверить версию файла.
  Ассистент живой сайт из своей среды не видит и должен прямо об этом говорить.

## 3. Кэш: главный источник «у меня старая версия»

- Браузер угадывает срок жизни файла по его возрасту и может показывать старую копию часами. Поэтому:
  **стили и скрипты подключаются с меткой содержимого** (`style.css?v=<хэш>`, `build_site.py` делает это сам);
  **скачиваемые файлы получают метку в имени** (пример из основного сайта: `Trosha-na-ekrane-1d765321.zip`);
  **постоянный адрес для скачивания** делается страницей, которая читает `latest.json` через `fetch(..., {cache: 'no-store'})`
  и сама ведёт на актуальный файл (см. `main`, папку `trosha/zip/`).
- В `.htaccess` лежит правило `no-cache` для html и служебных файлов, но оно работает только там, где запросы доходят до Apache.
  На nginx то же задаётся в его настройках.
- Мессенджеры (Telegram, MAX) кэшируют карточку ссылки; чтобы обновить, к адресу добавляют `?v=…`.

## 4. Поиск (SEO)

- Страница политики конфиденциальности: `noindex` и не в `sitemap.xml`; главная в `sitemap.xml`; на каждой странице `canonical`.
- `robots.txt`: закрыть служебное (`/tests/`, `/tools/`, `/docs/`), в конце `Sitemap:`. Для Яндекса полезно `Clean-param: v`
  (`?v=` в ссылках не создаёт новых страниц). Пока `"draft": true`, закрыто всё.
- Яндекс Вебмастер: мета-тег подтверждения (поле `yandex_verification`), потом отправить `sitemap.xml` и главную на переобход.
  Google Search Console: подтверждение через HTML-тег. Обе настройки делает владелец сайта в своём кабинете.
- Раздел «Вопросы и ответы» выводится ещё и разметкой `FAQPage` (`build_site.py` делает это сам; видимый текст и разметка совпадают).
- Шрифт Rubik лежит у нас (`fonts/`), не на серверах Google. Картинка для ссылок: лёгкий JPEG 1200×630 (`images/og.jpg`).
- Живой пример основного сайта: после выкладки он сообщал Яндексу об обновлениях (IndexNow). Для нового сайта это можно добавить,
  когда будет домен и ключ.

## 5. Проверки и CI

- `tests/check_site.py` работает за секунды, без браузера и сети: данные, свежесть собранных файлов, закрытые теги, живые ссылки и якоря,
  запрет заглушек при запуске. Она же в GitHub Actions на каждый PR в `new-site`.
- **Почему без браузера.** На основном сайте проверка с настоящим браузером (Playwright) несколько раз зависала на установке браузера
  у самого GitHub (сеть раннера) и ломала слияния. Для статичных страниц она не нужна. Внешний вид проверяется вручную:
  скриншоты на телефоне (390 px) и компьютере (1280 px), без горизонтальной прокрутки.
- Если проверка CI упала не из-за наших файлов (сеть раннера и т. п.), её можно перезапустить **один раз**; второй провал считается настоящим.

## 6. Релизы и откат

- После каждого слияния PR в `new-site` workflow «Release» создаёт релиз `site-v<версия>` (версия в `data/site.json`).
  Релизы не помечаются «последними», потому что в репозитории живут релизы основного сайта и ссылка `releases/latest/…` принадлежит им.
- GitHub **не позволяет токену workflow** ставить метки на старые коммиты, где менялись файлы `.github/workflows` (ошибка 403), поэтому
  прошлые версии задним числом не отмечаются: метки появляются только на новых слияниях.
- Откат описан в README (`git checkout site-vX -- .` в новой ветке и PR). Он не стирает историю.

## 7. Оформление

- Шрифт Rubik, тёплая палитра (оранжевый `#ff6a1f` / `#e2500c`, кремовый фон, тёмно-коричневый текст), панели с радиусом 20 px,
  кнопки-«пилюли». Всё меняется в `data/site.json` (`colors`) и `assets/style.css`.
- Телефон важнее компьютера: сначала проверяем узкий экран, без горизонтальной прокрутки, цель нажатия не меньше 44 px.
- Анимации уважают `prefers-reduced-motion`. У картинок всегда есть `alt`.

## 8. Что осталось в `main` и сюда не переносилось

Прогулка-квест (`progulka/`), карта и маршруты, озвучка (ElevenLabs), страница «Троша на экране панели» и её архив для флешки,
форма отзывов (функция в Яндекс Облаке и модерация через GitHub), анонимный счётчик запусков, выкладка на старый хостинг по FTP,
приложение для Android (отдельный репозиторий). Если что-то из этого понадобится новому сайту, берём из `main`
(`git show main:путь`) и подстраиваем.

## 9. Как подставлять новые данные

1. Заказчик присылает в чате название, описание, тексты, фото, контакты, адрес сайта (список в README).
2. Ассистент раскладывает их по `data/site.json`, картинки кладёт в `images/` (сжатые: JPEG/WebP, ширина до 1600 px), собирает
   страницы, запускает `tests/check_site.py`, смотрит скриншоты на телефоне и компьютере.
3. PR в `new-site`, показ заказчику, слияние после «сливай». Когда сайт готов к запуску: `"draft": false`, подтверждение в Вебмастере,
   настройка домена и сервера (раздел 2).
