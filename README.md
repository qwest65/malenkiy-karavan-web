# Статичный сайт (ветка `new-site`)

Основа для нового статичного сайта на других данных. Сделана из проекта «Маленький караван»: те же вёрстка,
шрифт, правила проверки, выкладки и релизов, но без прогулки, карты, озвучки и Троши. Всё, что нужно знать о том,
как мы с вами работаем и почему сделано так, записано в [`docs/CONTEXT.md`](docs/CONTEXT.md).

> ⚠️ **Эту ветку не сливать в `main`.** В `main` живёт «Маленький караван», слияние затёрло бы его сайт.
> Работаем так: правки приходят PR-ами **в `new-site`**. Оригинал сайта «Маленького каравана» остаётся в `main`.

**Состояние сейчас: черновик** (`"draft": true` в `data/site.json`). Сайт на заглушках, закрыт от поисковиков
(`noindex` и `Disallow: /`). Данные пока не подставлены.

## Как это устроено

| Что | Где |
|---|---|
| Весь контент: название, тексты, карточки, вопросы, контакты, цвета | `data/site.json` |
| Вёрстка страниц (то, что превращает данные в HTML) | `tools/build_site.py` |
| Стили; шрифт Rubik лежит у нас, а не на серверах Google (из России они грузятся плохо) | `assets/style.css`, `fonts/` |
| Картинки | `images/` (значок `icon.png`, карточка для ссылок `og.jpg`, заглушка `placeholder.svg`) |
| **Готовые страницы** (их отдаёт сервер, на сервере ничего собирать не нужно) | `index.html`, `privacy.html`, `404.html`, `sitemap.xml`, `robots.txt` |
| Проверка перед выкладкой | `tests/check_site.py`, `.github/workflows/checks.yml` |
| Автоматические релизы с метками версий | `.github/workflows/release.yml`, `tools/make_release.sh` |

## Как поменять сайт

1. Правите `data/site.json` (тексты, карточки, вопросы, контакты) и кладёте картинки в `images/`.
2. `python3 tools/build_site.py` пересобирает страницы. Результат коммитится вместе с данными.
3. `python3 tests/check_site.py` проверяет, что всё сходится (то же самое делает CI на каждый PR).

Типы разделов: `text` (абзацы), `cards` (карточки с картинкой), `faq` (вопросы и ответы, с разметкой для
поисковиков), `contacts` (подпись, значение, ссылка). Разделов можно любое количество, порядок как в файле.
Нужен другой вид (галерея, таблица цен, форма) — скажите, добавим тип раздела в `tools/build_site.py`.

## Что прислать, чтобы заполнить сайт

- Название сайта, короткий подзаголовок, описание для поисковиков (1–2 предложения).
- Адрес сайта (домен) и где он будет жить.
- Тексты разделов (о проекте, услуги/возможности, вопросы и ответы, контакты, политика конфиденциальности).
- Фотографии и логотип (для карточек, значка и картинки ссылки в мессенджерах).
- Цвета, если есть фирменные (иначе останутся тёплые оранжевые).
- Код подтверждения Яндекс Вебмастера, если сайт подтверждаем (поле `yandex_verification`).

Когда данные подставлены, в `data/site.json` ставим `"draft": false`: проверка сама не пропустит сайт, если в нём
остались заглушки.

## Запуск

Сайт статичный: достаточно любого хостинга, который отдаёт файлы из папки. Схема, которой пользуется основной
сайт: свой сервер сам забирает ветку раз в пару минут (`git pull`), а домен и сертификат настроены отдельно
(подробности и грабли: `docs/CONTEXT.md`). Для этой ветки делается **отдельный клон ветки `new-site`**
в отдельной папке: `git clone -b new-site <адрес репозитория> /srv/sites/<домен>`.

## Версии и откат

После **каждого слияния PR в `new-site`** workflow «Release» создаёт релиз на странице
[Releases](https://github.com/qwest65/malenkiy-karavan-web/releases) с меткой `site-v<версия>`: `site-v0.1`, если
версия в `data/site.json` новая, иначе `site-v0.1.1`, `site-v0.1.2` и так далее. Эти релизы не помечаются
«последними», чтобы не подменять релизы основного сайта.

Откатить сайт на версию (история сохраняется, откат можно отменить):

```bash
git fetch origin && git checkout -b rollback-site-v0.1 origin/new-site
git rm -rq . && git checkout site-v0.1 -- .          # файлы ровно как в версии site-v0.1
git commit -m "Откат на site-v0.1" && git push -u origin rollback-site-v0.1
# откройте PR в new-site и слейте его; новый релиз создастся сам
```

Или скажите ассистенту: «откати сайт на site-v0.1».
